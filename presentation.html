改掉一個 bug,多出三個 bug。

WHAT IS TDD · 測試驅動開發

什麼是 TDD?

它在上世紀末就被提出 —— 一個並不新的老點子。

普通開發
01先寫功能
02再隨便測一下
VS
TDD
01先寫測試
02再寫功能
WHY TDD · 為什麼值得

TDD 的優勢

01
目標絕對清晰 對寫程式的人來說,測試沒過,就代表功能是壞的——好壞有明確標準,不靠感覺。
02
改動有保障 以後改完程式,先跑測試確保沒弄壞既有功能,改得安心。

從此,告別壞代碼。

REALITY CHECK · 現實骨感

看起來很美好,實際上呢?

人類真正用起來,會撞上這幾道牆。

✕
反直覺、門檻高 面對空白檔案,大部分人寫不出測試;需求一模糊,更是無從下手。
✕
一改就報廢 辛苦寫的測試,需求一改就變廢紙。
✕
老闆不買賬 在老闆眼裡,不開發、只寫測試,就是在浪費時間。

「後期 bug 會變少」這種話,老闆不信。真的埋頭實作,就準備看隔壁同事快速交付、升你主管,再留一坨屎山給你。

AI'S COMFORT ZONE · 反轉

反人類的 TDD,卻是 AI 的舒適區

對人類反直覺的事,對 AI 剛剛好。

INPUT 文字需求 自然語言,會有歧義
──▶ AI 轉譯
SPEC 測試代碼 精準無歧義,比中文更好懂
──▶ AI 按測試寫
OUTPUT 實作代碼 又快又好

人類的痛點,正好是 AI 的強項。

BUT TDD ALONE · 還不夠

但光靠 TDD,還有問題

測試只保證「程式對」,不保證「需求對」。

✕
測試過 ≠ 需求對 測試通過,不代表符合用戶需求。測試與需求之間有鴻溝——PM 與工程師的理解偏差,往往就出現在這。
✕
測試代碼很難讀 看久了就是煩;就算請 AI 在測試裡加中文註解,也一樣。
用戶需求 理解鴻溝 測試代碼
THE ILLUSION · 幻象

只有 TDD 的幻象

功能沒 BUG,卻根本不是我要的東西。

測試用例
✓ 是人 ✓ 身體不好 ✓ 脾氣不好
需求 / WANT 林黛玉 弱柳扶風的病美人
測試
全過 ✓
實際 / GOT 中年禿頭 coder 三條測試,一條不差地全中

沒有 BUG,但根本不是我要的。

BDD · 登場

BDD 登場

Behaviour Driven Development · 行為驅動開發

用自然語言描述需求,人要 review 的是需求本身,而不是一行行代碼。

看測試代碼 ──▶ 看自然語言需求

但自然語言 ≠ 隨便說。開發遊戲只說「要很好玩」,等於什麼都沒說。

GHERKIN · 把需求說清楚

用 Given / When / Then 說清楚需求

場景 · SCENARIO
Given
前提條件 在什麼情況下
When
觸發動作 使用者做了什麼
Then
預期結果 應該發生什麼
REAL EXAMPLE · US 後台實戰

真實範例:傭金結算篩選

commission-statement.feature
Scenario: 依結算狀態篩選為已產生
Given 我在 /commission-statement 頁面
When 我選擇 settlement_status = 已產生
And 我點擊「查詢」
Then 表格只顯示 settlement_status = 已產生 的紀錄
And 分頁總數反映篩選結果
WHY NOBODY USES IT · 叫好不叫座

這麼好,怎麼沒人用?

PM 「PRD 都寫好了,幹嘛還要寫這鬼東西?」 對 PM 來說,是多出來的學習成本。
工程師 「不是要跟 PM 溝通的話,我直接寫測試程式更快。」 多寫一層,純粹浪費時間。

結論 在人類團隊裡,維持這套機制——成本過高。

IN THE AI ERA · 局勢翻轉

但在 AI 時代,局勢翻轉

工程師兼任 PM 與技術指導,寫程式,變成 AI 的事。

01
寫測試用例超快 把需求丟給 AI,Given / When / Then 一下就生出來。
02
主動確認邊界細節 寫完還會回頭問清楚——例如 settlement_status 到底有哪些值。
03
準確轉成程式 按測試輸出實作,對 AI 來說輕而易舉。

維持 BDD 的成本,在 AI 時代趨近於零。

TWO SAFEGUARDS · 雙保險

約束 AI 的雙保險

TDD 防止改出 Bug 守住「程式是對的」
AI 被雙重約束
BDD 符合需求 守住「做的是對的東西」

兩道防線,讓 AI 又快、又不出包。

SDD 登場

Spec Driven Development · 規格驅動開發

✓ TDD ──▶ ✓ BDD ──▶ SDD
WHAT IS SDD · 規格驅動

SDD 是什麼?

先把一份完整的「規格 Spec」寫清楚,讓它成為 AI 開發的唯一事實來源。

SINGLE SOURCE OF TRUTH 規格 Spec 人類維護的對象
──▶
› 需求 › 測試 › 程式 › 任務拆解

人類維護規格,程式只是產物。

BEFORE · 原本的做法

原本,我是這樣做的

只請 AI 看 API 文件,生成對應的 interface 來實作。

INPUT API 文件 唯一的輸入
──▶ AI 解析
GENERATE interface 依文件生成對應介面
──▶ 照介面寫
IMPLEMENT 實作 把功能補上

整個起點,只有一份 API 文件。

WHY IT BROKE · 不夠用了

後來,interface 不夠用了

需求變多、功能連動,光一份介面撐不住。

✕
需求爆量、彼此連動 功能越來越多,還牽扯業務邏輯的上下文,功能與功能之間互相影響。
✕
要記的更多了 需求紀錄得寫下功能之間的關聯,不再只是單一介面長什麼樣。

真實案例:手動上下分 vs 出入金審核 差在哪?我搞錯了,害後端還得花時間幫我確認功能。

只靠 API 文件生的 interface,已經不夠用了。

ANOTHER PROBLEM · 文檔失效

還有一個坑:spec 會過期

spec 沒跟著程式走,文檔就會反過來騙人。

01 改了程式卻沒更新 spec——例如後端改了 API interface,文檔就失效了。
02 AI 看了失效的文檔,反而被文檔騙。
03 我只好回頭手動修 spec。

手動是能管——但人,總會忘記。

THE FIX · 防坑

解法:強制一致性

CLAUDE.md
## 一致性要求
要改程式?先改文檔描述,再動手寫。
spec 與程式,永遠保持一致。

但 AI 有時還是會忘。文件一多,就得建立同步機制來把關。

防坑,真的很重要。

ASK FIRST · 反問機制

漏說的細節,讓 AI 改錯

我漏講的細節,常常讓 AI 默默改錯。

AI 早該回頭問的細節
? i18n 名詞一致嗎(代理ID vs 代理編號) ? 狀態到底有哪幾類

我是 AI 的老闆——它沒問就埋頭動手,那就是它的錯。「我沒說清楚,它就不該回頭問我嗎?」

建立反問機制:開工前先問問題、確認邊界,再動手。

讓邊界浮現,細節不再漏。

PLAN MODE · 先規劃再動手

讓 AI 自己設計步驟

先規劃、再動手,AI 的注意力更集中。

PLAN MODE /plan AI 自己設計步驟,注意力提升
──▶ 規劃
TASKS 生成 task 拆成可執行清單
──▶ 我審核 ✓
BUILD 照步驟實作 一步步完成

我能審核計畫、確認方向,保證他不會走偏。

THE CORE VALUE · spec 的核心

這,就是 spec 的核心價值

對我 / FOR ME 輕鬆審核 一眼看懂,好把關
SPEC 核心價值
對 AI / FOR AI 注意力聚焦 只做該做的事,不發散

一份好 spec,讓人放心、讓 AI 專心。
